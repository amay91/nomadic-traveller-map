# Implementation Plan: TravelMap

This file covers *how* to build what [`product_spec.md`](./product_spec.md) describes: the locked decisions, the stack, the file layout, the geometry pipeline, the runtime architecture, and the order of work. Status lives in [`tasks.md`](./tasks.md).

**Method, carried over from Pāntha and the Portfolio Dashboard, then scaled down.** Pāntha's practices were built for a large, commercial-grade app. This app is ~1% of that size, and its brief says *lightweight, efficient, design-led*. The practices that survive are the cheap, high-value ones: **fixture/data tests first, mockup before build, a design study archived with its decisions, a spec kept current, the real artifact inspected before "done"**. The ones that don't survive are there because they would cost more than this app does: CI pipelines, PR change control, Playwright suites, defect registers, staged hosting. That call follows Pāntha's own L14 proportionality clause.

## 0. Locked decisions

| # | Decision | Rationale |

| L1 | **Vanilla HTML + CSS + JS. No framework, no bundler, no transpiler, no runtime dependencies.** Classic `<script>` tags, not ES modules. **A real consequence, found building Phase 1, not theoretical:** classic scripts share ONE global scope across files, and a top-level `function` declaration is a `var`-like global even across separate `<script>` tags — so `logic.js` declaring `function search(){}` and `app.js` later doing `const { search } = Logic` throws `SyntaxError: Identifier 'search' has already been declared`, a parse-time error that silently kills the whole page (zero rendered output, no visible error unless the console is checked directly). **Fix, now the standing pattern for every file that isn't the final `app.js`:** wrap the file's internals in one IIFE and expose only a single namespaced global (`window.Logic`), never bare function names. | Module scripts are blocked on `file://`, and the app must open by double-click (spec §4.1). A ~500-line app gains nothing from React/Vite except upgrade chores. |
| L2 | **Geometry is pre-projected at dev time and committed.** `tools/build-geo.mjs` turns Natural Earth 1:50m (`world-atlas@2`) into SVG path strings in `app/geo.js`. The browser never projects, simplifies, or parses TopoJSON. | Removes d3 + topojson (~60 KB) and every per-load CPU cost. The trade-off: changing projection or detail means re-running one script, which happens about once a year. |

## 2. The geometry pipeline (`tools/build-geo.mjs`)

1. Load `world-atlas/countries-50m.json` (Natural Earth admin-0, 241 features).
2. **Simplify** with Visvalingam weights over spherical triangle area, keeping the top *KEEP* fraction of vertices. The KEEP value is chosen at T2 by comparing renders side by side.
3. **Group into three, not two:** join atlas features to the 195 by ISO numeric code (`countries`); anything left over is checked by its display name against `app/countries.js`'s `TERRITORIES` table (`extras` — clickable, tracked, styled exactly like a country); anything matching neither stays `territories` (inert land, spec §5.2's 6 exclusions). Somaliland → Somalia and N. Cyprus → Cyprus are dissolved in with `topojson.merge`, so no internal border shows. Antarctica is dropped.
4. **Split overseas regions** off France and the Netherlands (French Guiana, Guadeloupe, Martinique, Réunion, Mayotte, Caribbean Netherlands) into their own `extras` entries: any polygon whose centroid falls outside Europe is assigned to the nearest known anchor point. **Caribbean Netherlands needs *two* anchor points**, not one — Bonaire sits far south near Venezuela, while Sint Eustatius and Saba sit ~500 km north, close enough to Guadeloupe's anchor to be nearest-point-matched into the wrong territory. Found by inspecting real per-polygon centroids after simplification (a duplicate `iso` turning up in `extras` was the tell), not assumed; the general lesson — one anchor per real geographic cluster, not one per territory — is worth remembering if a future territory has the same split-population shape.
5. **Project** (L7) and serialize each feature as a compact **relative** SVG path. Coordinates are rounded to 0.1 unit and handled as integer tenths, so rounding error never accumulates. Consecutive duplicate points and rings that collapse below 3 points are dropped.
6. **Dots, applied identically to `countries` AND `extras`** (one shared `place()` function, not two code paths): anything whose projected area is < 6 units², *or* whose path came out empty after simplification, gets an anchor at the centroid of its *largest* polygon (Kiribati and Fiji straddle the antimeridian, so a whole-feature centroid would land in open ocean) and a dot fallback. Tuvalu (below 1:50m resolution) gets a hand-placed anchor. **This uniform treatment is what recovered three real places** — Saint Barthélemy, Pitcairn Islands, Norfolk Island — that the old territories-only path had silently dropped: inert `territories` never got a dot fallback, so anything too small to survive simplification as a path just vanished with no error. `territories` (the 6 truly inert areas) keeps the old path-only behavior, since nothing there is meant to be clickable.
7. Emit `app/geo.js`: `window.GEO = { w, h, c: {code: path}, a: {code: [cx,cy,x0,y0,x1,y1]}, d: [code...], t: [[name, path]] }` — one flat `c`/`a`/`d` namespace covering both the 195 and the 45 territories; `app/countries.js`'s two arrays are what tell the app which is which. The script throws if any of the 195 **or** the 45 territories ends up with neither a shape nor a dot, or if a `TERRITORIES` entry never matched a feature at all.

**A third split, added when Svalbard turned out to be fixable (2026-09-13):** Norway's raw shape fuses in Svalbard and Jan Mayen exactly the way France's fuses in French Guiana — but a plain nearest-point split (like `splitOverseas`, step 4) doesn't work for it. Norway's own mainland runs unusually far north (Nordkapp, 71.17°N), close enough in raw degree-distance to Svalbard's location (74–80°N) that real Norwegian polygons would get pulled toward the wrong anchor. `splitNorway` uses a verified rule instead — checked against every real polygon centroid at this simplification level, not assumed: `longitude < 0° OR latitude > 72.5°` is Svalbard/Jan Mayen, everything else is mainland Norway, with a genuine gap on both sides (mainland tops out at 71.05°N; the Svalbard cluster starts at 74.45°N; Jan Mayen sits alone at 71.03°N/‑8.4°E, caught by the longitude half of the rule since its latitude alone is right in the ambiguous range). **The general lesson, worth remembering before adding a fourth split-country:** a nearest-point-to-anchor method is only as good as the assumption that the "home" territory is compact around one center — it silently breaks for any country whose own shape is unusually elongated or extends unusually far toward a territory's location, and the fix each time was to verify against the real centroids rather than assume the existing method generalizes.

Regenerate with `cd tools && npm install && node build-geo.mjs`. The measured detail/size trade-off is recorded in `tasks.md` T2.

## 3. Runtime architecture (`app.js`)

No framework, so the structure is plain functions around one state object:

```
state = { visits: {ISO: [years]}, selected: ISO|null, view: {x,y,w,h}, sort: {col, dir} }

boot()      → load storage → renderMap() (one innerHTML write) → paint() → bind events
paint()     → toggle .is-visited on each path/dot (class flips; CSS handles the colour + transition)
select(iso) → .is-selected (CSS scale via transform-box: fill-box) → raise the element in the draw order → openPopover()
save(iso, years) → state + storage → paint() → ripple(iso) → bumpCounter() → toast(undo snapshot)
flyTo(iso)  → tween the viewBox to the element's getBBox(), padded, with a zoom cap
panel       → renderTable() from state + logic.stats(); sort on header click; row click → flyTo + select
```

- **Places vs. countries:** `app.js` builds one `PLACE` map merging `COUNTRY` (official: true) and `TERRITORY` (official: false) by code, since a country and a territory never share one. Everything that resolves a code — search, tooltip, popover, table row — reads `PLACE`; everything that *counts* toward "of 195" (the header pill, the table's official total) filters to `official: true` first. This is the one seam a territory addition has to respect; get it backwards and a territory either can't be found or silently inflates the header count.
- **Event delegation:** one listener on the `<svg>` handles every clickable place (country or territory), so there are 3 listeners total, not 240.
- **Hover and tooltip:** `pointermove` on the svg, reading `data-iso` from `event.target`. The tooltip is one absolutely positioned div, moved with `transform`.
- **Zoom/pan:** the viewBox is the camera. Wheel zooms around the cursor. Two-pointer pinch and pointer-drag pan. Borders use `vector-effect: non-scaling-stroke` so they stay hairline at any zoom, and dots are counter-scaled so they stay the same size on screen. **The zoom-toward-cursor math must clamp the requested width/height BEFORE computing the recentring offset, not after** — a real bug (found 2026-09-13, verifying the Svalbard fix by zooming in near the map's very top edge): scrolling in past the zoom cap kept sliding the view further away, tick after tick, ending up thousands of kilometres from the cursor. The offset was being computed from the *unclamped* requested size while `apply()` silently substituted the clamped size, so every over-zoom tick introduced a small, compounding error. Fixed by clamping inside `zoomAt` itself, using the exact same bound `apply()` enforces, so the two can never disagree. Worth remembering for any future zoom-adjacent change: the anchor-preserving offset math is only correct if it's computed against the size that actually gets applied.
- **Motion** is CSS transitions wherever possible (fill, transform, opacity). JS `requestAnimationFrame` is used only for the viewBox tween and the ripple.
- **Reduced motion:** a single `@media (prefers-reduced-motion: reduce)` block zeroes every duration, and the JS tweens check the same media query.

`logic.js` holds everything that has no DOM, so Node tests can load it through `vm`:
- `normalize(s)`: lowercase and strip accents (NFD + remove combining marks).
- `search(q, places)`: seven tiers — exact-name > exact-alias > name-prefix > alias-prefix > name-substring > alias-substring > general substring; ties between a country and a territory favour the country. **The exact tiers exist because a real bug demanded them**, found by `tests/logic.test.mjs`, not assumed: without a distinct "exact match" rank, "uk" ranked *Ukraine* (a prefix match on its own real name) above *United Kingdom* (a complete, exact match on its alias "UK") — a 5-tier scheme that only distinguished prefix/substring couldn't tell "typed the whole thing" from "just happens to start the same." Returns at most 8 results.
- `parseYears(s, maxYear, allowRange)` → `{ years }` or `{ error }`: splits on `,` `;` or whitespace; each token is a plain 4-digit year, or — only when `allowRange` is true (F21, added 2026-09-14 for Lived/Home) — a period `YYYY-YYYY` (closed) or `YYYY-` (open, ongoing). A parsed entry is a plain `number` or `{from, to}`, `to: null` meaning ongoing.
- `stats(visits)` → `{ count, pct, byContinent, territoryCount }` — `count`/`pct`/`byContinent` are official-195-only (what the header pill and "of 195" line show); `territoryCount` is the separate "+N territories visited" line (spec F7), never merged into the others. **Status (F16) never enters this function**: Visited/Lived/Home all count the same, so there is no `status` filter to get wrong here.
- `encodeMap(visits)` / `decodeMap(str)`: the URL codec (spec F17). Round-trip must be lossless, and `decodeMap` must drop any code that isn't a known country or territory — a link is untrusted input, and a mangled one must not be able to invent places. A period (F21) is wrapped `~…~` — `~` never otherwise appears, since place entries are joined by `-`, not `~` — with 2 base-36 chars (from) meaning ongoing, or 4 (from+to) meaning closed; an unterminated `~` (a mangled link) is dropped rather than misparsed into whatever follows.
- `yearsOf(code)` / `statusOf(code)`: the only two readers of a record's shape. Everything else in the app goes through them, so the `{y, s}` record shape has exactly two places to change if it ever moves again.
- `validateImport(obj)` → sanitized visits or an error. All-or-nothing.

## 6. Go-live: GitHub Pages

**Is it possible? Yes — this app is a better fit for GitHub Pages than most.** It's already 100 % static (HTML/CSS/JS, zero server, L1), every asset reference in `app/` is relative with no leading slash (verified directly: `index.html`'s script/link tags, `manifest.webmanifest`'s `start_url`/`scope`, `service-worker.js`'s `SHELL` list — all `./…`), so the whole app already works correctly served from a subpath like `/TravelMap/`, which is exactly what a GitHub Pages *project* site is. No code changes are needed for hosting itself.

**Hosting here also fixes two things real-file limits have been holding back, not just "makes it reachable by URL":**
- **F17 (save-by-link) starts working as originally designed.** L15's fix (2026-09-14) made "Email me this map" fall back to Export on a `content:`/`file:` origin, because `location.href` is meaningless there. On a real `https://…github.io/…` URL, the *original* branch runs: a genuine link that reopens the exact map on any device, no fallback needed.
- **F20 (PWA/offline/install) starts working at all.** Service workers refuse to register on `file://`/`content://` — confirmed back in Phase 1 (B11), which is why that verification needed a real `http://localhost` dev server. GitHub Pages serves over real HTTPS, so install-to-home-screen and the offline cache (and the Safari 7-day-eviction exemption that's the whole reason F20 exists) all become real, not just locally-tested.

**Why GitHub Pages over Cloudflare Pages/Netlify, which L13/§4.5 previously named as the preference:** that preference was about keeping a serverless-functions option open for the L13 multi-user trigger, which hasn't fired. The owner has asked for GitHub Pages specifically, matching an existing pattern (PortfolioDashboard) they already know how to operate. **This supersedes the earlier preference for this app** — L13's hedges (the `Store` seam, a versioned/portable blob) don't depend on which static host is used, so nothing about the multi-user deferral is weakened by this choice. If L13's trigger ever fires, migrating static hosts is a redeploy, not a rewrite.

**A real privacy issue this plan surfaced, resolved before anything else here matters:** GitHub Pages' free tier requires the source repo to be **public**. Scanning the docs turned up the owner's actual real travel/residency history hard-coded as the design study's demo fixture (`docs/design-studies/01-map/index.html`'s old `SAMPLE`) plus narrative mentions of the same specifics (exact residency years, a real personal file path, a specific city) in `product_spec.md`, `tasks.md`, and `NOTES.md`. **Scrubbed 2026-09-14** (D0, done) — the fixture is now fictional data, and the narrative mentions keep the design *reasoning* (why real data was used, the privacy discipline applied reading it, the India/Germany judgment calls) without the personal specifics that used to illustrate it. The shipped app itself (`app/`) never held any of this — `visits = Store.load() || {}` always starts empty — so this was a docs-only issue, not an app one, but it would have gone public either way if unscrubbed.

**Repo structure decision: publish `app/` via a GitHub Actions workflow, not a `/docs` folder or a `gh-pages` branch.** GitHub Pages' two other options either force renaming/duplicating `app/` (a `/docs`-folder source can't point at an arbitrary subfolder like `/app`) or maintaining a second branch by hand. A workflow that uploads `app/` as the Pages artifact needs neither — the repo layout stays exactly as documented everywhere else in this doc set, and `tests/`/`tools/`/the `.md` docs are simply never part of what's served, without needing to move or gitignore them.

**Case sensitivity, a real Windows-vs-GitHub-Pages gotcha worth stating before it bites:** this project was built on Windows, whose filesystem is case-insensitive; GitHub's servers are not. A reference that happens to differ in case from the real filename (`Icons/` vs `icons/`, say) can work every time locally and 404 the moment it's hosted. Worth one pass over `app/`'s own references before or right after the first deploy (D4 covers this) — not expected to find anything, since everything was already written lowercase-consistent, but cheap to actually check rather than assume.

**What does NOT need to change:** `manifest.webmanifest`'s `start_url`/`scope`, `service-worker.js`'s `SHELL` paths, every `<script>`/`<link>` in `index.html` — all already relative, verified directly rather than assumed (§ above). No `base` tag, no path-rewriting, no build step to inject a repo-name prefix — the zero-build architecture (L1) pays for itself again here.

**The single-file build (`nomadic-traveller-map.html`, `tools/build-single.mjs`) stays, but changes role.** It was built as a workaround for exactly the `content://` problem L15 documents — it remains useful as an install-free, works-from-anywhere offline copy, but once a real hosted URL exists, that URL becomes the primary, canonical way to use and share the app; the single file is the fallback, not the main path. No action needed — this is a framing note for the docs, not a task.
